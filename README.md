# Egress audit for a local AI stack

A RAG application can answer questions using local models and still attempt to contact external services. This repository shows how to test that behavior: block outbound **IPv4** traffic from the stack's Docker bridge, record attempted connections, and attribute them to individual services.

**Reproduce three tests:** a pre-staged run with cached models, a cold-start run with empty caches, and a hardened run with offline settings enabled. The steps below cover the full setup, capture, and comparison workflow.

**Test environment:** Ubuntu 24.04 under WSL2, with the RAG services on a dedicated Docker bridge (`br-rag`). We focused on IPv4 traffic from that network. See [Audit coverage](#audit-coverage) for the boundaries of the test.

**Start here:** Read [Requirements](#requirements), then follow steps 1 through 6 in order. To inspect existing evidence instead, see [Results and evidence](#results-and-evidence). To audit a different deployment, see [Adapting the audit](#adapting-the-audit-to-your-own-stack).

## How the audit works

We keep the Docker network running and reject outbound IPv4 connections instead of disconnecting the machine. This lets components attempt connections while we capture the evidence.

- **Firewall:** `audit/egress-deny.sh` adds rules to Docker's `DOCKER-USER` chain. It permits communication within `br-rag` and established or related replies, while rejecting other matching outbound IPv4 packets. When kernel logging is supported, rejected packets appear under `EGRESS-BLOCK`.
- **DNS sinkhole:** The audit overlay points each service at a local dnsmasq server. It records queried hostnames and answers external lookups with `198.51.100.1`, a documentation-only address. It forwards nothing to a public resolver.
- **Packet capture:** `tcpdump` records traffic on `br-rag` while the workload runs.

Each service has a fixed IPv4 address, allowing us to associate **observed** traffic with the originating container.

| Evidence | What it tells you | What it misses |
| --- | --- | --- |
| DNS log | Which hostnames a service resolved through the sinkhole | Connections to literal IP addresses |
| Packet capture | Outbound packets visible on the bridge during the capture | Events outside the capture window and host traffic |
| Kernel firewall log | Packets logged and rejected under the firewall policy | Events lost to log rate limits or unavailable logging |

Use all three records together. They show destinations and attempts, not the contents of encrypted requests.

## Results and evidence

The original runs are preserved in `results/`. **The counts below are logged blocked packets, not unique API requests or confirmed data transfers.**

| Test | What happened | Blocked packets |
| --- | --- | ---: |
| Pre-staged | The cached RAG stack answered the patient-records question | 52 |
| Cold-start | Missing model files prevented the query from completing | 32 |
| Hardened | Offline settings eliminated observed Ollama, app, and Phoenix attempts in the test window; one VectorAI DB usage notification was blocked | 1 |

The hardened result is **not zero attempted egress**. The remaining attempt was blocked at the network boundary.

Each test saves these artifacts:

| File | Purpose |
| --- | --- |
| `*.dns.log` | DNS queries recorded by the sinkhole |
| `*.kernel.log` | Firewall entries with the `EGRESS-BLOCK` prefix |
| `*.pcap` | Captured network packets |
| `*.tcpdump.txt` | Capture report, including kernel drop counts |
| `*.summary.txt` | Output generated by `audit/summarize.sh` |

To reproduce the existing summaries from the checked-in evidence:

```bash
sudo ./audit/summarize.sh results/prestaged
sudo ./audit/summarize.sh results/cold
sudo ./audit/summarize.sh results/hardened
```

**New test runs write into `capture/`.** Preserve the original files in `results/` so you can compare the runs.

## Requirements

- Linux with Docker Engine and the Compose plugin. The experiment used **Ubuntu 24.04 under WSL2**, with Docker Engine installed inside Ubuntu.
- `sudo`, `iptables`, `tcpdump`, and permission to read kernel messages using `dmesg`.
- Around **12 GB RAM** for the stack.
- An internet connection during the initial installation and model-staging steps.
- **Two terminals** for each capture: one for Docker and the query, another for `tcpdump`.

**Use a test environment.** The commands adjust Docker firewall rules, clear the kernel message buffer with `dmesg -C`, and temporarily move model and data directories during the cold-start run. Keep production data and logs separate.

Run these commands with Docker Engine on the same Linux host where `br-rag` is visible to `iptables` and `tcpdump`. The capture commands are designed for that setup, rather than Docker Desktop's separate networking environment.

## 1. Prepare and test the stack (internet available)

```bash
mkdir -p local_data ollama_data phoenix_data hf_cache model_cache
sudo chown -R 999:999 local_data
docker compose up -d
docker exec ollama ollama pull llama3.2:3b
docker compose build app
docker compose run --rm app --question "How long are adult patient records kept?"
```

The application should answer using the synthetic documents in `docs/`. Confirm it works before blocking connections. VectorAI DB runs as UID 999 inside its container, so that user must own the local data directory.

## 2. Verify DNS and firewall logging

Run every command from the repository root. Open two terminals, one for the stack and one for the packet capture, and set this in each:

```bash
export COMPOSE_FILE=docker-compose.yml:docker-compose.audit.yml
```

Build the sinkhole and start the stack with it:

```bash
docker compose build dns
docker compose up -d
```

Test the sinkhole before starting an isolated run. The answer should be the reserved address `198.51.100.1`, and the hostname should appear in the DNS log:

```bash
docker compose run --rm --entrypoint python app -c "import socket; print(socket.gethostbyname('huggingface.co'))"
sudo cat capture/dns.log
```

Test a connection to a literal IP address, which would bypass DNS logging. It should fail, typically with `ConnectionRefusedError`:

```bash
sudo ./audit/egress-deny.sh on
docker compose run --rm --entrypoint python app -c "import socket; socket.create_connection(('1.1.1.1', 443), timeout=5)"
sudo ./audit/egress-deny.sh status
sudo dmesg | grep EGRESS-BLOCK | tail -3
sudo ./audit/egress-deny.sh off
```

If the firewall reports `Firewall-level logging: UNAVAILABLE`, blocking still works but the kernel log cannot provide complete firewall evidence. Record this limitation. The last command switches the test policy back off.

## 3. Pre-staged run: check cached-model behavior

Start with the model and embedding files already cached locally. This run shows which external connections services attempt after the setup dependencies are present, and whether the RAG query still completes. We warmed caches online for this experiment; a physically air-gapped installation would use approved offline transfer procedures.

Warm the caches with the network open. `-f docker-compose.yml` runs the app without the sinkhole so downloads can complete:

```bash
sudo ./audit/egress-deny.sh off
docker compose -f docker-compose.yml run --rm app --question "How long are adult patient records kept?"
sudo ls model_cache
```

`model_cache` should contain a `models--BAAI--bge-small-en-v1.5` folder. LlamaIndex stores the embedding model in its own cache folder, separate from Hugging Face's usual location, which is why the compose file keeps both.

Terminal 1:

```bash
docker compose down
docker compose up --no-start
sudo ./audit/egress-deny.sh on
sudo truncate -s 0 capture/dns.log
sudo dmesg -C
```

Check that `egress-deny.sh` printed `Firewall-level logging: enabled`. `dmesg -C` clears the kernel log so it only holds this run.

Terminal 2 (leave it running):

```bash
sudo tcpdump -i br-rag -nn -s 0 -w capture/prestaged.pcap 2>&1 | tee -i capture/prestaged.tcpdump.txt
```

Terminal 1:

```bash
docker compose up -d
docker compose run --rm app --question "How long are adult patient records kept?"
```

The question may take several minutes because some libraries retry blocked registry checks before loading cached files. Save the successful response if you also want functional evidence.

When the answer prints, leave the stack idle so calls on a timer can fire:

```bash
sleep 1800
```

Then press Ctrl+C in Terminal 2, and in Terminal 1:

```bash
sudo cp capture/dns.log capture/prestaged.dns.log
sudo TZ=UTC dmesg --time-format iso > capture/prestaged.kernel.log
sudo ./audit/summarize.sh capture/prestaged | tee capture/prestaged.summary.txt
```

Save the component logs before you stop the stack, because `docker compose down` deletes them:

```bash
docker logs vectorai > capture/prestaged-vectorai.log 2>&1
docker logs ollama > capture/prestaged-ollama.log 2>&1
docker logs phoenix > capture/prestaged-phoenix.log 2>&1
```

## 4. Cold-start run: expose setup dependencies

This run moves the active model caches and disposable test data into `.warm` backup folders to reveal what the stack tries to download when starting without local dependencies. **Do not run these directory operations against production data.**

Terminal 1:

```bash
docker compose down
sudo mv ollama_data ollama_data.warm && mkdir ollama_data
sudo mv hf_cache hf_cache.warm && mkdir hf_cache
sudo mv model_cache model_cache.warm && mkdir model_cache
sudo mv phoenix_data phoenix_data.warm && mkdir phoenix_data
sudo mv local_data local_data.warm && mkdir local_data && sudo chown -R 999:999 local_data
docker compose up --no-start
sudo ./audit/egress-deny.sh on
sudo truncate -s 0 capture/dns.log
sudo dmesg -C
```

Terminal 2:

```bash
sudo tcpdump -i br-rag -nn -s 0 -w capture/cold.pcap 2>&1 | tee -i capture/cold.tcpdump.txt
```

Terminal 1. The model pull and the question are both expected to fail:

```bash
docker compose up -d
docker exec ollama ollama pull llama3.2:3b
docker compose run --rm app --question "How long are adult patient records kept?"
sleep 1800
```

Ctrl+C in Terminal 2, then:

```bash
sudo cp capture/dns.log capture/cold.dns.log
sudo TZ=UTC dmesg --time-format iso > capture/cold.kernel.log
sudo ./audit/summarize.sh capture/cold | tee capture/cold.summary.txt
```

Save the component logs before stopping the stack, because `docker compose down` deletes them:

```bash
docker logs vectorai > capture/cold-vectorai.log 2>&1
docker logs ollama > capture/cold-ollama.log 2>&1
docker logs phoenix > capture/cold-phoenix.log 2>&1
```

Component logs often name the exact URL each call was trying to reach.

## 5. Restore the cached working stack

```bash
docker compose down
sudo ./audit/egress-deny.sh off
sudo rm -rf ollama_data hf_cache model_cache phoenix_data local_data
sudo mv ollama_data.warm ollama_data
sudo mv hf_cache.warm hf_cache
sudo mv model_cache.warm model_cache
sudo mv phoenix_data.warm phoenix_data
sudo mv local_data.warm local_data
unset COMPOSE_FILE
docker compose up -d
```

`unset COMPOSE_FILE` returns Compose to the base configuration. Check the paths before running the cleanup commands: they remove temporary cold-start folders and restore the `.warm` backups.

## 6. Hardened run: verify offline settings


Apply documented offline settings and repeat the pre-staged workload under the firewall. Compare network activity and verify that the query still works. Check that the RAG query still completes, then compare the connection attempts with the earlier runs.

`docker-compose.hardened.yml` applies the setting each vendor documents:

| Component | Setting | Documented effect |
| --- | --- | --- |
| Ollama | `OLLAMA_NO_CLOUD=1` | Runs Ollama in local-only mode, without cloud features |
| Arize Phoenix | `PHOENIX_ALLOW_EXTERNAL_RESOURCES=false` | Stops Phoenix's own public-internet requests, for air-gapped environments |
| Arize Phoenix | `PHOENIX_TELEMETRY_ENABLED=false` | Turns off analytics tracking |
| Hugging Face libraries | `HF_HUB_OFFLINE=1` | Uses only the local cache |
| VectorAI DB | No setting applied | Keeps its defaults; the DNS sinkhole and egress firewall block its deployment ping |

Start from the pre-staged state (step 5 restores it). Terminal 1:

```bash
export COMPOSE_FILE=docker-compose.yml:docker-compose.audit.yml:docker-compose.hardened.yml
docker compose down
docker compose up --no-start
sudo ./audit/egress-deny.sh on
sudo truncate -s 0 capture/dns.log
sudo dmesg -C
```

Terminal 2 (leave it running):

```bash
sudo tcpdump -i br-rag -nn -s 0 -w capture/hardened.pcap 2>&1 | tee -i capture/hardened.tcpdump.txt
```

Terminal 1. Start the stack, confirm the settings took effect, then ask a question before and after the 10-minute mark:

```bash
docker compose up -d
docker exec ollama printenv OLLAMA_NO_CLOUD
docker inspect phoenix --format '{{range .Config.Env}}{{println .}}{{end}}' | grep PHOENIX_
docker compose run --rm --entrypoint printenv app HF_HUB_OFFLINE
docker compose run --rm app --question "How long are adult patient records kept?" 2>&1 | tee capture/hardened-q1.txt
sleep 720
docker compose run --rm app --question "How long are adult patient records kept?" 2>&1 | tee capture/hardened-q2.txt
sleep 1200
```

The Phoenix image has no `printenv`, so its settings are read with `docker inspect`. Then press Ctrl+C in Terminal 2, and in Terminal 1 save the logs before stopping the stack:

```bash
docker logs vectorai > capture/hardened-vectorai.log 2>&1
docker logs ollama > capture/hardened-ollama.log 2>&1
docker logs phoenix > capture/hardened-phoenix.log 2>&1
sudo cp capture/dns.log capture/hardened.dns.log
sudo TZ=UTC dmesg --time-format iso > capture/hardened.kernel.log
sudo ./audit/summarize.sh capture/hardened | tee capture/hardened.summary.txt
sudo ./audit/egress-deny.sh off
docker compose down
unset COMPOSE_FILE
```

### What the hardened run recorded

The hardened summary records two DNS lookups from VectorAI DB for `elspv.pervasive.com` (A and AAAA), one outbound TCP connection attempt to `198.51.100.1:443`, and one firewall block. The capture report records zero packets dropped by the kernel. No other component appears in the recorded outbound attempts.

The network controls blocked the remaining attempt. The result applies to this workload, test window, and Docker IPv4 bridge. It cannot rule out later calls or traffic from other interfaces.

## Reading the summary

`summarize.sh` prints four sections:

1. **DNS lookups.** Each hostname, who asked, the record type, and when it was first seen.
2. **Connection attempts leaving the stack.** From the packet capture.
3. **Firewall blocks.** From the kernel log.
4. **Coverage.** How many entries each record holds, packets the capture dropped, whether the kernel rate-limited firewall messages, and what all three records miss.


## Adapting the audit to your own stack

1. **Put your services on one bridge network** with a fixed interface name (`com.docker.network.bridge.name`) and a fixed subnet.
2. **Give each service a fixed address** with `ipv4_address`, and add matching names to the `label()` function in `audit/summarize.sh`.
3. **Point each service's `dns` setting at the sinkhole** in an overlay file like `docker-compose.audit.yml`.
4. **Set `BRIDGE`** in `audit/egress-deny.sh` and the `-i` interface in the `tcpdump` command to your bridge name.
5. **Run your own representative workload** in place of the sample question, and keep the idle window long enough to catch calls on a timer.

## Audit coverage

The experiment captures **outbound IPv4 activity from the `br-rag` Docker network** while the test workload runs. We also retain DNS and firewall logs to identify attempted connections that a packet capture alone might miss. The firewall allows established or related replies, so each restricted run starts with fresh service connections.

Host processes, traffic on other interfaces, and browser requests outside this bridge are outside the capture. **IPv6 verification is still pending** and can be added once tested. The logs identify attempted destinations, although encrypted request contents and calls outside the observation window remain unknown.

This setup tests firewall-enforced isolation. A physical air gap also requires controls over other network paths and software transfers. If you adapt the audit to another environment, document the interfaces and protocols you monitor.
